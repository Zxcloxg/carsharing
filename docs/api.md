# REST API booking-service: ресурс «Автомобиль» (ПР2)

Формальный контракт: [`booking-service/openapi.yaml`](../booking-service/openapi.yaml)
(OpenAPI 3.0.3). Примеры запросов и ответов: [`examples.http`](examples.http).

## 1. Описание сущности

Основная сущность предметной области — **автомобиль автопарка** (`Car`).
Вокруг неё строится всё остальное: бронь ссылается на машину, поездка
считает стоимость по её тарифу, телеметрия присылает её координаты.

| Поле | Тип | Обязательное | Ограничения | Описание |
|---|---|---|---|---|
| `id` | string (UUID) | — (только чтение) | генерируется сервером | Идентификатор автомобиля |
| `plate` | string | да | 4–10 символов, `^[A-Z0-9-]{4,10}$`, уникален | Госномер; приводится к верхнему регистру |
| `brand` | string | да | от 2 до 50 символов | Марка |
| `model` | string | да | от 1 до 50 символов | Модель |
| `year` | integer | да | от 1990 до текущего года + 1 | Год выпуска |
| `color` | string \| null | нет | от 2 до 30 символов | Цвет кузова |
| `price_per_minute` | number | да | больше 0, максимум 2 знака после запятой | Тариф за минуту аренды, тенге |
| `fuel_level` | number | нет (по умолчанию `1.0`) | от 0 до 1 | Доля топлива или заряда |
| `status` | string | нет (по умолчанию `free`) | `free`, `booked`, `in_rent`, `service` | Текущее состояние машины |
| `created_at` | string (ISO 8601) | — (только чтение) | UTC | Когда добавлена в автопарк |
| `updated_at` | string (ISO 8601) | — (только чтение) | UTC | Когда изменена последний раз |

Жизненный цикл статуса: `free` → `booked` (US-2) → `in_rent` (US-3) → `free`;
`service` выставляет оператор вручную (US-5).

## 2. URI и операции

Базовый префикс — `/api/v1`. Имя ресурса — существительное во множественном
числе (`cars`), вложенности нет, глаголов в путях нет: действие выражает
HTTP-метод.

| Метод | Путь | Назначение | Успешный код |
|---|---|---|---|
| GET | `/api/v1/cars` | Список машин с пагинацией и фильтрами | 200 |
| POST | `/api/v1/cars` | Добавить машину в автопарк | 201 + заголовок `Location` |
| GET | `/api/v1/cars/{id}` | Получить одну машину | 200 |
| PUT | `/api/v1/cars/{id}` | Полностью заменить данные машины | 200 |
| PATCH | `/api/v1/cars/{id}` | Частично обновить (например, только статус) | 200 |
| DELETE | `/api/v1/cars/{id}` | Убрать машину из автопарка | 204 (без тела) |

Коды ошибок, общие для ресурса:

| Код | Когда возвращается |
|---|---|
| 400 | Не прошла валидация тела запроса или query-параметров |
| 404 | Машины с таким `id` нет |
| 405 | Метод не поддерживается для этого пути |
| 409 | Госномер уже занят другой машиной |

## 3. Пагинация и фильтрация

`GET /api/v1/cars` никогда не отдаёт всю таблицу целиком.

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `page` | integer ≥ 1 | 1 | Номер страницы |
| `limit` | integer 1–100 | 10 | Размер страницы |
| `status` | enum | — | Фильтр по статусу |
| `brand` | string | — | Фильтр по марке, подстрока без учёта регистра |
| `max_price_per_minute` | number > 0 | — | Не дороже указанного тарифа |

Ответ — объект-страница, а не голый массив: клиент должен знать, сколько
всего записей.

```json
{ "items": [ /* Car */ ], "page": 1, "limit": 10, "total": 3, "pages": 1 }
```

Пример: `GET /api/v1/cars?page=1&limit=10&status=free&brand=kia`

## 4. Валидация и единый формат ошибок

Входные данные проверяются **до** бизнес-логики схемами DRF
([`fleet/serializers.py`](../booking-service/fleet/serializers.py)): типы,
обязательность, границы чисел, длины строк, перечисления, регулярное
выражение госномера. Некорректный запрос не доходит до слоя хранения и
никогда не превращается в 500.

Любая ошибка API имеет одинаковую форму:

```json
{
  "error": "Validation failed",
  "details": [
    {"field": "plate", "message": "This value does not match the required pattern."},
    {"field": "brand", "message": "This field is required."}
  ]
}
```

- `error` — краткое человекочитаемое сообщение;
- `details` — список уточнений (пустой, если уточнять нечего); для ошибок
  валидации в нём по одному элементу на каждое проблемное поле.

Единство формата обеспечивает обработчик
[`fleet/errors.py:api_exception_handler`](../booking-service/fleet/errors.py) —
он подключён в `REST_FRAMEWORK["EXCEPTION_HANDLER"]` и приводит к этому виду
как ошибки DRF (400/404/405), так и доменные исключения (`CarNotFound`,
`PlateAlreadyUsed`).

## 5. Архитектура: слои

Код разделён так, что каждый слой знает только о соседнем снизу:

```
HTTP-запрос
   │
   ├─ fleet/urls.py          маршруты (пути → представления)
   ├─ fleet/views.py         слой маршрутов: разобрать, провалидировать, отдать код ответа
   ├─ fleet/serializers.py   схемы валидации (DTO) — правила для входных данных
   ├─ fleet/services.py      бизнес-логика: уникальность номера, фильтры, пагинация
   ├─ fleet/repository.py    хранение: сейчас потокобезопасный словарь в памяти
   └─ fleet/errors.py        доменные исключения и единый формат ошибок
```

Хранение по условию ПР2 временное (в памяти). Весь остальной код обращается
к нему только через интерфейс репозитория, поэтому переход на PostgreSQL в
ПР3 затронет один файл — `repository.py`.

## 6. Проверка

```bash
cd booking-service
python -m venv .venv && source .venv/Scripts/activate   # Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
python manage.py runserver 8010      # API на http://localhost:8010
python manage.py test fleet          # 13 автотестов: CRUD, валидация, пагинация, фильтры
```

Все примеры в [`examples.http`](examples.http) — реальные ответы запущенного
сервиса, снятые через `curl`.
