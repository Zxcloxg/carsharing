# Автотесты и покрытие (ПР5)

Код тестов: [`booking-service/tests/`](../booking-service/tests). Проверка безопасности и
чек-лист — в [`security.md`](security.md).

## Запуск

```bash
cd booking-service
pip install -r requirements.txt -r requirements-dev.txt   # coverage и PyYAML — только для тестов
python manage.py test tests                 # все 278 тестов (Windows: test.cmd)
python manage.py test tests.unit            # только модульные — без базы, меньше секунды
python manage.py test tests --shuffle       # в случайном порядке
python -m coverage run manage.py test tests && python -m coverage report   # с покрытием (Windows: coverage.cmd)
python -m coverage html                     # HTML-отчёт: booking-service/htmlcov/index.html
```

Для API-тестов нужен запущенный PostgreSQL с параметрами из `.env` (как для самого сервиса):
Django сам создаёт базу `test_<DB_NAME>`, накатывает на неё миграции и удаляет её после прогона.

### Модульные тесты бизнес-логики

Правила предметной области вынесены из сервисов в чистые функции
[`fleet/domain.py`](../booking-service/fleet/domain.py): всё, от чего зависит результат, включая
«сегодня», передаётся аргументом. Сервисы и схемы валидации вызывают эти функции, поэтому
тесты проверяют тот же код, что работает в API.

| Правило | Примеры проверок (`tests/unit/test_domain.py`) |
|---|---|
| Поминутная тарификация | Начатая минута оплачивается целиком (25 мин 1 с → 26 мин); минимум 1 минута; завершение раньше начала — ошибка, а не бесплатная поездка |
| Стоимость аренды | Тариф × минуты в `Decimal` без ошибок округления; используется тариф, зафиксированный в брони, а не текущий тариф машины |
| Возраст 18+ | Ровно в день 18-летия — можно; родившийся 29 февраля становится старше 1 марта |
| Допуск к аренде | Заблокирован → 403; ВУ не подтверждено → 403; уже есть активная аренда → 409; блокировка проверяется раньше ВУ |
| Водительское удостоверение | Нужна именно категория B («BE» и «C1» её не заменяют); дата выдачи не в будущем; истёкшее ВУ отклоняется; ВУ, истекающее сегодня, ещё действует |
| Пагинация | Смещение страницы; число страниц округляется вверх; пустой список — 0 страниц |

Остальные модульные тесты: схемы валидации (`test_validation.py`, 27), выпуск и проверка JWT,
включая `alg=none`, чужую подпись и токен без срока (`test_tokens.py`), декораторы ролей и
проверка владельца (`test_permissions.py`), обработчик ошибок (`test_errors.py`), хэширование
паролей и рабочие параметры Argon2id (`test_password_hashing.py`), ключ ограничителя частоты
(`test_throttling.py`).

### API-тесты: позитивный и негативный сценарий на каждую ключевую операцию

| Операция | Позитивный сценарий | Негативные сценарии |
|---|---|---|
| Регистрация | 201, email приведён к нижнему регистру, роль `customer` | 409 занятый email (в другом регистре), 400 слабый пароль, 400 попытка выбрать роль |
| Вход | 200 и подписанный токен, который открывает защищённый маршрут | 401 неверный пароль (ответ как для несуществующего email), 403 заблокированный аккаунт, 429 после 10 попыток |
| Машины: создание, чтение, замена, изменение, удаление | 201 + `Location`, 200, 204 | 400 без обязательного поля и с неверным типом, 409 занятый госномер, 404 неизвестный id, 409 удаление машины с бронями |
| Клиенты и ВУ | Профиль клиента, подача и одобрение ВУ открывают аренду | 400 младше 18 лет, 409 второе действующее ВУ, 409 повторное решение по ВУ, 409 одно ВУ для двух клиентов |
| Бронирование и оплата | Бронь занимает машину и фиксирует тариф; завершение считает стоимость и пишет платёж | 409 машина занята, 409 вторая аренда клиента, 403 ВУ не подтверждено, 409 повторное закрытие, откат всех таблиц при сбое на последнем шаге |
| Доступ по ролям | Оператор одобряет ВУ, администратор удаляет машину | 401 без токена, 403 роль без прав, 403 чужая бронь, профиль, ВУ |

### От какой ошибки защищает негативный тест — примеры

| Тест | Какую ошибку ловит |
|---|---|
| `test_spoofed_x_forwarded_for_does_not_reset_limit` | Лимит попыток входа обходится подменой заголовка — реальная ошибка, найденная в ПР5 |
| `test_operator_cannot_change_price` | Оператор ставит тариф 1 ₸/мин и катается бесплатно — реальная ошибка, найденная в ПР5 |
| `test_failure_on_last_step_rolls_back_whole_booking` | Бронь записана, а машина осталась «свободной» — если кто-то уберёт `@transaction.atomic` |
| `test_finish_before_start_is_rejected` | Сбой часов превращает поездку в бесплатную или «отрицательную» |
| `test_similar_categories_do_not_replace_b` | Проверка «есть ли буква B» вместо «есть ли категория B» пропустила бы права категории BE |
| `test_role_is_taken_from_database_not_from_token` | Понижённый администратор ещё час пользуется старым токеном |
| `test_same_license_cannot_be_approved_for_two_customers` | Аренда по чужому водительскому удостоверению |

## Изоляция тестовых данных

- **Отдельная база.** Тесты работают с `test_carsharing_full`, рабочая `carsharing_full` не
  затрагивается. Проверено: число строк в рабочей базе до и после прогона одинаково
  (`users 5, cars 5, customers 5, bookings 2, payments 1, car_status_history 8`), а тестовой
  базы после прогона нет в списке баз.
- **Транзакция на тест.** Каждый тест `ApiTestCase` (наследник `APITestCase`) выполняется в
  транзакции, которая откатывается после теста. Данные одного теста не видны другому.
- **Чистый кэш.** Счётчики ограничения частоты хранятся в кэше; `ApiTestCase.setUp` очищает его,
  поэтому тест на 429 не зависит от того, сколько входов сделали тесты до него.
- **Свои данные у каждого теста.** Тест сам создаёт нужные записи в `setUp` через фабрики
  `make_account`, `make_customer` и не рассчитывает на чужие.
- **Независимость от порядка.** Шесть прогонов с `--shuffle` (случайный порядок, seed
  8075664175, 1194176742, 8370087341, 63808382, 8785639680, 1785528946) и прогон с
  `--reverse` (обратный порядок) — везде 278 из 278. Повторить конкретный порядок можно,
  передав seed: `python manage.py test tests --shuffle 63808382`.
- **Найденная нестабильность.** Повторные прогоны выявили тест из ПР3, который иногда падал:
  в `test_only_one_paid_payment_per_booking` время завершения брони бралось через `now()` раньше,
  чем время начала, и при смене тика часов база отклоняла строку
  (`bookings_finish_after_start`). Теперь время начала фиксируется в `setUp`.

Пароли в тестах хэшируются тем же Argon2id, но с параметрами 1 МБ / 1 проход вместо 100 МБ / 2
(`tests/runner.py`). Иначе на машине с 3,5 ГБ памяти часть тестов падала с
`argon2 HashingError: Memory allocation error`. Рабочие параметры хэширования проверяет
отдельный тест.

### Слабо покрытые места

- **Админка Django** (`fleet/admin.py` 88,6 %, `accounts/admin.py`): не покрыты действия
  «Подтвердить выбранные удостоверения» и «Отметить инциденты решёнными». Это интерфейс
  сотрудников, проверялся вручную. Риск заметный: действие подтверждения ВУ обходит
  `services.review_license`. Если номер уже подтверждён у другого клиента, запись отклонит
  база, но сотрудник увидит ошибку 500 вместо понятного сообщения. Следующий шаг — тест через
  `admin.site` или перевод действия на сервис.
- **Методы `__str__` моделей** (`fleet/models.py`, `accounts/models.py`): используются только
  в админке, бизнес-логики в них нет.
- **Гонки** (`fleet/repositories/car_models.py`): ветка «ту же модель параллельно добавил другой
  запрос» срабатывает только при одновременных запросах. Нужен тест с двумя потоками и
  `TransactionTestCase`.
- **Защитные `raise`** (`fleet/repositories/common.py`, `accounts/repository.py`, `config/settings.py`
  — короткий `JWT_SECRET`): ветки «неизвестное нарушение ограничения базы» и неверная
  конфигурация. Путь до них через API не ведёт, это страховка.
- **Неиспользуемые параметры** (`status` в `payment_repository.search` и
  `driver_license_repository.search`): ни один маршрут их не передаёт. Это не пробел тестов, а
  лишний код, кандидат на удаление.
- **Ветка `BookingNotFound` внутри `close_booking`** (`fleet/services.py`): маршрут проверяет
  существование брони раньше, поэтому сюда можно попасть только при удалении брони между двумя
  запросами к базе.

Покрытие 98 % не означает, что ошибок нет: оно показывает, какой код хоть раз выполнялся.
Поэтому в ПР5 сделан упор на негативные сценарии и тесты, которые строят список проверок из
кода: маршруты из URLconf, сверка с `openapi.yaml`, обход всех исходников в поиске SQL.
