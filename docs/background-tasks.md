# Фоновое списание за поездку (ПР6)

Протокол проверки на живых процессах — [`async-scenario.md`](async-scenario.md).

## 1. Выбор сценария

Из трёх вариантов задания выбран **А — фоновая задача**: списание денег за поездку у
платёжного провайдера после её завершения.

| Вариант | Что это значило бы для каршеринга | Почему не он |
|---|---|---|
| **А. Фоновая задача** | Завершение поездки не ждёт банк: поездка закрывается сразу, деньги списываются в фоне с повторами | **Выбран** |
| Б. Кэширование | Кэшировать каталог свободных машин | Статус машины меняется при каждой брони и завершении, а клиенту нельзя показать уже занятую машину как свободную. Кэш с TTL здесь даёт устаревшие данные, а запрос и так обслуживает индекс `cars_status_created_idx` (ПР3) |
| В. Внешняя интеграция | Геокодирование адреса машины | Координаты машин — зона `telemetry-service`, который пока скелет. Платёжный провайдер — тоже внешний сервис, и в варианте А мы вызываем его по HTTP с тайм-аутом и повторами |

**Почему именно списание.** В каршеринге клиент завершает поездку, стоя у машины.
Ответ «поездка завершена» должен прийти сразу: машина освобождается для следующего
клиента, а арендная минута перестаёт тикать. Банк-эквайер отвечает за 1–3 секунды,
иногда не отвечает вовсе. До ПР6 списание шло прямо внутри запроса (`charge()` в
`close_booking`): медленный банк замедлял завершение поездки, а недоступный банк
превращал его в ошибку, и поездка не закрывалась. Теперь поездка закрывается всегда, а
списание выполняет обработчик очереди: он повторяет попытки, при неудаче фиксирует долг,
и клиент может оплатить заново. Так работают реальные каршеринги: «поездка завершена,
оплата обрабатывается».

## 2. Механизм: стандартный API `django.tasks` и очередь в PostgreSQL

В Django 6 есть встроенный API фоновых задач — `django.tasks`: декоратор `@task`,
`Task.enqueue()`, `TaskResult` со статусом `READY / RUNNING / SUCCESSFUL / FAILED`, сигналы
`task_enqueued / task_started / task_finished`. Однако в поставке только два бэкенда:
`ImmediateBackend` выполняет задачу сразу внутри запроса, то есть не в фоне, а
`DummyBackend` не выполняет её никогда. Поэтому задачи объявлены стандартным API
(`fleet/tasks.py`), а бэкенд написан свой — `jobs.backends.DatabaseBackend`. Он хранит
очередь в таблице `background_tasks` той же PostgreSQL. Выполняет задачи отдельный процесс
`python manage.py run_worker` (`jobs/worker.py`).

| Альтернатива | Почему не она |
|---|---|
| `ImmediateBackend` из Django | Выполняет задачу внутри запроса — ровно то, от чего уходим |
| Поток или `asyncio` внутри процесса API | Задача теряется при перезапуске или падении процесса; статус не виден другим процессам; повторы и паузы пришлось бы писать вручную |
| Celery / RQ + Redis или RabbitMQ | Нужен отдельный брокер (на этой машине Docker не работает), ещё один сервис в эксплуатации. Главное — постановка задачи в брокер не входит в транзакцию базы: при откате останется задача без платежа, а при сбое брокера после COMMIT появится платёж без задачи |
| **Своя очередь в PostgreSQL за API `django.tasks`** | Задача — это `INSERT` в той же транзакции, что и платёж (**атомарно**: при откате не остаётся ни платежа, ни задачи). Новой инфраструктуры нет, задачи переживают перезапуск. Код задач написан на стандартном API: при росте нагрузки бэкенд меняется в настройке `TASKS` (например, на Celery-совместимый) без правки `fleet/tasks.py` |

## 3. Как это работает

```mermaid
sequenceDiagram
    autonumber
    participant C as Клиент
    participant API as booking-service (API)
    participant DB as PostgreSQL
    participant W as run_worker
    participant P as Платёжный провайдер

    C->>API: PATCH /bookings/{id} {"status":"finished"}
    API->>DB: BEGIN; закрыть бронь, стоимость; INSERT payments (pending);<br/>INSERT background_tasks (READY); освободить машину; COMMIT
    API-->>C: 200 + payment {status: pending, task: READY} (≈0,25 с)
    loop каждые 0,5 с
        W->>DB: SELECT … WHERE status='READY' AND run_after<=now()<br/>FOR UPDATE SKIP LOCKED → RUNNING, attempts+1
    end
    W->>P: POST /v1/charges, Idempotency-Key: payment.id, timeout 5 с
    alt 201 — списано
        W->>DB: payments → paid; INSERT задача send_receipt; task → SUCCESSFUL
    else нет связи, тайм-аут, 5xx, 429 — временный сбой
        W->>DB: task → READY, run_after = now + 2 с · 2^(n−1), ошибка в errors
        Note over W: WARNING в логе; после 3-й попытки — FAILED
    else 402 / 4xx — отказ банка
        W->>DB: task → FAILED сразу, без повторов
    end
    Note over W,DB: task_finished(FAILED) → payments → failed + причина
    C->>API: GET /payments/{id} — статус платежа и задачи
    C->>API: POST /bookings/{id}/payments — повторить оплату → 202 Accepted
```

**Задачи** (`fleet/tasks.py`):

| Задача | Когда ставится | Что делает |
|---|---|---|
| `charge_payment(payment_id)` | При завершении поездки (`close_booking`) и при повторной оплате (`retry_payment`) | Вызывает провайдера; при успехе — платёж `paid` и постановка `send_receipt` в одной транзакции |
| `send_receipt(payment_id)` | Только после успешного списания | Письмо-чек клиенту. Локально — консольный почтовый бэкенд, в тестах — `locmem` |

**Таблица `background_tasks`** (`jobs/models.py`, миграция `jobs/0001`):

| Колонка | Назначение |
|---|---|
| `task_path`, `args`, `kwargs` | Что выполнить: `fleet.tasks.charge_payment` и `{"payment_id": "…"}` |
| `status` | `READY` → `RUNNING` → `SUCCESSFUL` или `FAILED` (статусы `django.tasks`) |
| `attempts`, `max_attempts` | Сколько попыток было и предел (CHECK `attempts <= max_attempts`) |
| `run_after` | Не раньше этого момента — время постановки или следующей попытки |
| `last_error`, `errors` | Краткая причина последнего сбоя и все сбои по попыткам со стектрейсами |
| `return_value`, `worker_ids` | Результат успешной задачи и обработчики, бравшие её |

Частичный индекс `background_tasks_ready_idx (queue_name, priority DESC, run_after) WHERE
status = 'READY'` обслуживает выборку обработчика и не растёт от выполненных задач.

**Платёж** (`payments`, миграция `fleet/0003`) получил колонки `task_id` и
`failure_reason` и два ограничения: не больше одного `pending`-платежа на поездку
(повторная оплата не запустится поверх идущей) и обязательная причина у `failed`.

## 4. Устойчивость к сбою

| Ситуация | Поведение |
|---|---|
| Провайдер не отвечает: отказ соединения, тайм-аут 5 с, 5xx, 429 | `PaymentProviderUnavailable` — временная ошибка. Повтор через 2 с, затем через 4 с (экспоненциальная пауза, `jobs/retry.py`). Пока идут повторы, платёж остаётся `pending` |
| Попытки исчерпаны (3 из 3) | Задача `FAILED`, сигнал `task_finished` переводит платёж в `failed` с причиной. Клиент повторяет оплату: `POST /api/v1/bookings/{id}/payments` → **202 Accepted** + `Location` |
| Банк отказал: 402, прочие 4xx | `PaymentDeclined` (наследник `PermanentTaskError`) — повтор не поможет, задача `FAILED` сразу, без лишних запросов к банку |
| Ответ потерялся, хотя списание прошло (тайм-аут после списания) | Повтор идёт с тем же `Idempotency-Key = payment.id`, провайдер возвращает то же списание. **Двойного списания нет** |
| Обработчик убит посреди задачи | Задачу в `RUNNING` дольше `LEASE_SECONDS` (300 с) забирает другой обработчик. Повтор безопасен благодаря идемпотентности |
| Несколько обработчиков | `SELECT … FOR UPDATE SKIP LOCKED`: строку, которую взял один обработчик, другие пропускают |
| База недоступна | Цикл обработчика ловит `DatabaseError`, пишет ERROR в лог, ждёт и продолжает работу, не падая |
| Задача удалена из кода | Задача сразу получает `FAILED` с причиной `Unknown task`, обработчик продолжает работу |

Настройки — переменные окружения (`.env.example`): `TASK_MAX_ATTEMPTS=3`,
`TASK_RETRY_BACKOFF_SECONDS=2`, `TASK_RETRY_BACKOFF_MAX_SECONDS=300`,
`TASK_LEASE_SECONDS=300`, `PAYMENT_PROVIDER_URL`, `PAYMENT_PROVIDER_TIMEOUT=5`.

## 6. API

| Метод | Путь | Назначение | Доступ |
|---|---|---|---|
| PATCH | /api/v1/bookings/{id} | Завершение: **200** сразу, в ответе `payment` в статусе `pending` со статусом задачи | вход (своя) |
| GET | /api/v1/payments/{id} | Статус платежа и его задачи: попытка, следующая попытка, последняя ошибка | вход (свой) |
| POST | /api/v1/bookings/{id}/payments | Повторить оплату после сбоя: **202 Accepted** + `Location: /api/v1/payments/{id}`; 409 — поездка не завершена, уже оплачена или списание ещё идёт | вход (своя) |
| GET | /api/v1/tasks | Очередь: фильтры `status`, `task`, пагинация | staff |
| GET | /api/v1/tasks/{id} | Задача целиком: попытки и причины сбоев, без стектрейсов | staff |

Стектрейсы наружу не отдаются (ПР5, OWASP API8). Они хранятся в `background_tasks.errors`
и видны в админке Django, где оператор может перезапустить сбойную задачу действием
«Запустить заново».

## 7. Как проверить вручную

Нужны запущенный PostgreSQL, `python manage.py migrate` и `seed_demo`. В `booking-service/`
откройте три окна:

```bash
./payment_provider.cmd        # 1) эмулятор провайдера: http://127.0.0.1:8030, ответ за 1,5 с
./serve.cmd                   # 2) API: http://127.0.0.1:8010
./worker.cmd                  # 3) обработчик очереди — сюда смотреть логи
```

**Штатный путь** (запросы — в [`examples.http`](examples.http), разделы 54–58):
войдите как `daniyar@example.kz`, забронируйте свободную машину, завершите поездку.
Ответ придёт сразу с `payment.status = pending`. Через 1,5–2 с `GET /api/v1/payments/{id}`
покажет `paid`, а в окне обработчика появятся строки «попытка 1 из 3» и «выполнена за
1.5 с» и текст чека.

**Ошибочный путь:** остановите окно 1 (Ctrl+C) и снова забронируйте и завершите
поездку. Ответ по-прежнему придёт сразу. В окне обработчика появятся три попытки:
WARNING «Повтор через 2 с», «Повтор через 4 с», затем ERROR «попытки исчерпаны» и «Платёж
… не прошёл». Платёж получит статус `failed` с причиной. API всё это время отвечает.
Запустите провайдер снова (`./payment_provider.cmd --fail-first 1` — первое списание
он отклонит с 503) и повторите оплату `POST /api/v1/bookings/{id}/payments`: ответ —
**202**, платёж оплатится со второй попытки.

**Отказ банка:** `./payment_provider.cmd --decline-over 50` — любое списание больше 50 ₸
получит 402. Задача завершится сбоем с первой попытки, без повторов.

**Автоматически:** `./async_check.cmd` сам запускает три процесса, проходит оба пути и
восстановление и пишет протокол в [`async-scenario.md`](async-scenario.md). Полные логи
процессов скрипт сохраняет в `booking-service/.async-check/`.

## 9. Ограничения и развитие

* Клиент узнаёт результат опросом `GET /payments/{id}`. В мобильном приложении это
  должно быть push-уведомление: его можно поставить задачей рядом с `send_receipt`.
* Опрос очереди раз в 0,5 с даёт задержку до 0,5 с и небольшую нагрузку на базу. При
  росте нагрузки можно перейти на `LISTEN/NOTIFY` PostgreSQL или сменить бэкенд `TASKS`
  на брокер.
* Отложенный запуск (`run_after`) уже поддерживается. На нём делается следующая задача
  бэклога D2 — автоматическое снятие брони, не начатой за 15 минут.
* Эмулятор провайдера — учебная замена настоящего эквайринга. Клиент
  `fleet/payment_gateway.py` работает с любым HTTP-провайдером с таким же контрактом
  (URL задаётся в `PAYMENT_PROVIDER_URL`).
