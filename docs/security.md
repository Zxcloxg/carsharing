# Проверка безопасности API (ПР5)

Сервис `booking-service` проверен по списку типовых рисков
[OWASP API Security Top 10 (2023)](https://owasp.org/API-Security/editions/2023/en/0x11-t10/).
Каждый пункт проверялся тремя способами:

1. **Автотесты** [`booking-service/tests/security/`](../booking-service/tests/security) — 45 тестов,
   идут в общем прогоне `python manage.py test tests` и ловят возврат уязвимости.
2. **Запросы к запущенному сервису** — скрипт
   [`booking-service/security_check.py`](../booking-service/security_check.py), 70 проверок на
   реальной базе PostgreSQL. Прогон до исправлений —
   [`security-check-before.md`](security-check-before.md) (63 из 70, расхождений 7), после —
   [`security-check.md`](security-check.md) (70 из 70).
3. **Чтение кода** там, где снаружи не видно: как DRF определяет клиента для лимита, какие поля
   отдаёт слой хранения, есть ли SQL из строк.

Статусы: **выполнено** — проверено, проблем нет; **исправлено** — проблема найдена и устранена
(запись «до/после» ниже); **не применимо** — в сервисе нет того, к чему относится риск.

## Чек-лист

### Обязательные пункты задания

| № | Что проверено | Как проверено | Результат | Статус |
|---|---|---|---|---|
| 1 | **Инъекции**: параметризованные запросы/ORM, а не конкатенация строк | Статический тест обходит синтаксическое дерево всех `.py` проекта и ищет `raw()`, `extra()`, `RawSQL`, `cursor.execute()` с непостоянным запросом. Динамически: SQL-фрагменты в фильтрах, в пути, в email и пароле при входе, в текстовом поле машины; символы `%` и `_` в фильтре | Все запросы строит ORM Django с параметрами. Единственный «сырой» SQL — константа `SHOW server_version` в `config/db.py`. Фрагмент `' OR '1'='1` в фильтре `brand` находит 0 машин, в числовом фильтре — 400, в пути — 404, в пароле — 401; марка `Robert'); DROP TABLE cars;--` сохраняется и возвращается как текст, таблица цела. `%` и `_` экранируются ORM и не превращаются в «любая строка» | выполнено |
| 2 | **Лишние поля в ответах** (хэш пароля и т. п.) | Тест рекурсивно обходит каждый ответ с учётной записью (регистрация, вход, `/auth/me`, список и карточка пользователей, профиль клиента, ответы с ошибками) и ищет ключи `pass`, `hash`, `secret`, `salt`, а в теле — строки `argon2` и пароль. Для учётной записи зафиксирован точный набор полей. Отдельно проверен состав JWT | Хэш пароля читается из базы только методом `find_credentials` для проверки при входе и сразу удаляется из словаря. Ответы содержат ровно `id, email, role, customer_id, is_active, created_at, last_login_at`. В токене только `sub, role, iss, iat, exp` — без email и персональных данных | выполнено |
| 3 | **Ограничение частоты запросов** на входе и регистрации | Тесты и живая проверка: 10 неверных паролей → 11-я попытка 429; то же с новым `X-Forwarded-For` в каждом запросе; вход с токеном в заголовке; регистрация 10 + 1 | Лимит 10/мин с IP был, но **обходился подменой `X-Forwarded-For`** (проблема 1), а **вход с любым действующим токеном падал с 500** (проблема 2) | **исправлено** |
| 4 | **Коды 401/403** на всех защищённых маршрутах | Тест берёт список маршрутов из URLconf и сверяет его с матрицей прав; каждый метод вызывается анонимом, клиентом, оператором и администратором, а также с испорченным токеном. Живая проверка — 40 запросов | 22 защищённых метода: без токена — 401 `not_authenticated` с `WWW-Authenticate: Bearer`, клиенту на маршруты персонала и оператору на маршруты администратора — 403 `permission_denied`. Испорченный токен — 401 даже на публичных маршрутах. Права проверяются раньше поиска записи, поэтому по коду ответа нельзя узнать, существует ли чужая запись | выполнено |

## Найденные и исправленные проблемы: до и после

### Проблема 1. Ограничение попыток входа обходится подменой `X-Forwarded-For`

**Риск:** API4/API2 — подбор пароля без ограничений. **Серьёзность:** высокая: лимит 10/мин из
ПР4 существовал только на бумаге.

**Как нашли.** В DRF клиента для ограничителя определяет `SimpleRateThrottle.get_ident`. При
`NUM_PROXIES = None` (значение по умолчанию, в проекте не задавалось) он берёт **весь заголовок
`X-Forwarded-For` как есть**, а этот заголовок присылает сам клиент. Новое значение в каждом
запросе — новый «клиент» и новый лимит.

**Воспроизведение:**

```bash
for i in $(seq 1 12); do
  curl -s -o /dev/null -w "%{http_code} " -X POST http://127.0.0.1:8010/api/v1/auth/login \
       -H "Content-Type: application/json" -H "X-Forwarded-For: 203.0.113.$i" \
       -d '{"email":"admin@carsharing.kz","password":"Guess#'$i'"}'
done
```

| | До исправления | После исправления |
|---|---|---|
| 12 попыток с разными `X-Forwarded-For` (протокол, п. 1.1–1.3) | `401` ×12 — перебор не ограничен | `401` ×10, затем `429 throttled` ×2 с `Retry-After` |

**Исправление.** `config/settings.py`: `REST_FRAMEWORK["NUM_PROXIES"] = TRUSTED_PROXY_COUNT`
(переменная окружения, по умолчанию `0`). При `0` адрес клиента — `REMOTE_ADDR` и
`X-Forwarded-For` от клиента игнорируется. Когда перед сервисом встанет API Gateway, ставится `1`:
адрес берётся из последнего звена заголовка, которое дописал сам шлюз, а присланное клиентом
по-прежнему не учитывается.

**Регрессионные тесты:** `tests/security/test_rate_limit.py`
(`test_spoofed_x_forwarded_for_does_not_reset_limit` для входа и регистрации,
`test_behind_gateway_real_client_taken_from_last_hop`, `test_proxy_count_is_configured`),
`tests/unit/test_throttling.py`.

### Проблема 2. Вход с токеном в заголовке — ошибка 500 и отдельный лимит на пользователя

**Риск:** API4 + надёжность. **Серьёзность:** средняя.

**Как нашли.** Автотест 401/403 перебирает все маршруты от имени всех ролей, в том числе
публичные `/auth/login` и `/auth/register` с токеном в заголовке, и получил 500 вместо 401/400.
Причина: для запроса с токеном `ScopedRateThrottle` считает попытки по `request.user.pk`, а у
объекта пользователя `CurrentUser` из ПР4 нет поля `pk` (`AttributeError`). Если бы `pk` был,
открылась бы вторая дыра: лимит считался бы по пользователю, и злоумышленник со своей
учётной записью получал бы отдельные 10 попыток на подбор чужого пароля, а с десятком
учётных записей — десять лимитов.

| | До исправления | После исправления |
|---|---|---|
| `POST /auth/login` с неверным паролем и токеном клиента (протокол, п. 5.40) | `500 internal_error` | `401 invalid_credentials` |
| 11-я попытка входа, на этот раз с токеном своей учётной записи | (500) | `429 throttled` — лимит по адресу общий |

**Исправление.** `accounts/throttling.py`: `ClientAddressThrottle` всегда считает попытки входа
и регистрации по адресу клиента, токен на счёт не влияет. В `CurrentUser` добавлено свойство
`pk` для совместимости с остальными компонентами DRF.

**Регрессионные тесты:** `test_public_auth_routes_accept_request_with_token`,
`test_own_token_does_not_give_separate_limit`, `tests/unit/test_throttling.py`.

### Проблема 3. Оператор может изменить тариф и госномер машины

**Риск:** API3 — Broken Object Property Level Authorization. **Серьёзность:** высокая для
бизнеса: оператор (или украденный токен оператора) ставит машине тариф 1 ₸/мин, после чего
бронирование почти бесплатно.

**Как нашли.** Сравнение матрицы прав из `docs/auth.md` («`PATCH /cars/{id}` — статус, топливо»
для оператора) с кодом: `PATCH /cars/{id}` закрыт декоратором `require_role(operator, admin)`,
но набор полей для оператора не ограничен.

| | До исправления | После исправления |
|---|---|---|
| Оператор: `PATCH /cars/{id}` `{"price_per_minute": 1}` (п. 4.3) | `200`, тариф стал **1.0** | `403 permission_denied`, в `details` — поле `price_per_minute` |
| Оператор: `{"plate": "HACK01"}` (п. 4.4) | `200`, госномер изменён | `403 permission_denied` |
| Тариф машины после попыток (п. 4.5) | 1.0 | 70.0 — не изменился |
| Оператор: `{"status": "service"}`, `{"fuel_level": 0.4}` | `200` | `200` — разрешённое осталось |

**Исправление.** `fleet/views.py`: для не-администратора `PATCH /cars/{id}` пропускает только
поля `OPERATOR_CAR_FIELDS = {status, fuel_level}`; проверка — новая функция
`ensure_fields_allowed` в `accounts/permissions.py` (права на уровне полей рядом с правами на
уровне ролей и записей). Запрос с запрещённым полем отклоняется целиком: разрешённое поле из
того же запроса тоже не применяется. Контракт `openapi.yaml` дополнен описанием.

**Регрессионные тесты:** `tests/security/test_property_level.py` (5 тестов),
`tests/unit/test_permissions.py::FieldLevelTests`.

### Проблема 4. Режим отладки включён и секретный ключ лежит в репозитории

**Риск:** API8 — Security Misconfiguration. **Серьёзность:** средняя.

**Как нашли.** Просмотр `config/settings.py`: `DEBUG = True` и
`SECRET_KEY = 'django-insecure-…'` остались из шаблона `startproject`, хотя параметры базы и
`JWT_SECRET` в ПР3–ПР4 уже вынесены в окружение. С `DEBUG = True` любой неизвестный адрес вне
`/api/` показывает отладочную страницу со списком маршрутов, включая адрес админки. Ключ
подписывает сессии и CSRF-токены админки, а раз он в git, он известен всем, у кого есть доступ к
репозиторию.

| | До исправления | После исправления |
|---|---|---|
| `GET /no-such-page` (п. 6.1) | Отладочная страница: «Using the URLconf defined in config.urls, Django tried these URL patterns: health, api/v1/, admin/ … You're seeing this error because you have DEBUG = True» | «Not Found. The requested resource was not found on this server.» |
| `SECRET_KEY` | строка в `config/settings.py` | `DJANGO_SECRET_KEY` из окружения, не короче 50 символов, без неё сервис не стартует |
| `DEBUG` | `True` в коде | `DJANGO_DEBUG`, по умолчанию выключен; включается только явным `true` |
| `ALLOWED_HOSTS` | `[]` (работало только из-за `DEBUG`) | `DJANGO_ALLOWED_HOSTS`, по умолчанию `localhost,127.0.0.1` |

**Исправление.** `config/settings.py` (функции `env_flag`, `env_list`), шаблон
`.env.example`. Старый ключ остаётся в истории git, поэтому считается скомпрометированным: в
`.env` сгенерирован новый.

**Регрессионные тесты:** `tests/security/test_configuration.py::DjangoSettingsTests`
(перечитывает модуль настроек с разным окружением).

## Что осталось и почему

| Риск | Почему не закрыт сейчас | Что сделать |
|---|---|---|
| Распределённый подбор пароля одной учётной записи с многих IP | Лимит по аккаунту (блокировка после N ошибок) позволил бы злоумышленнику блокировать чужие аккаунты — это отказ в обслуживании для клиента | Задержка, растущая с числом неудачных попыток на аккаунт, или капча после N ошибок |
| По ответу 409 `email_taken` при регистрации видно, что email занят | Обычный компромисс ради понятного сообщения; регистрация ограничена 10/мин с IP | При необходимости — подтверждение email с одинаковым ответом «письмо отправлено» |
| Вход в админку `/admin/` (сессии Django) не ограничен по частоте | Админка — не публичный API, она для сотрудников | Не пропускать `/admin/` через API Gateway наружу; ограничение частоты на шлюзе |
| JWT нельзя отозвать до истечения | Свойство JWT (обсуждалось в ПР4) | Срок 60 минут; блокировка и смена роли действуют сразу, потому что пользователь читается из базы |
| HTTPS | Шифрование канала — задача API Gateway (TLS), см. архитектуру | `SECURE_*`-настройки Django включаются вместе с развёртыванием за шлюзом |

## Почему проверка полная

На вопрос «если ничего не нашли — почему уверены» ответ здесь строится не на ручном переборе:

- **Маршруты берутся из кода.** Тест 401/403 получает список маршрутов из URLconf и падает, если
  у нового маршрута не указан уровень доступа. Забыть проверить новый эндпоинт нельзя.
- **Контракт сверяется с кодом.** Отдельный тест требует, чтобы маршруты в `openapi.yaml` и в
  коде совпадали, поэтому незадокументированных эндпоинтов нет.
- **SQL ищется во всех файлах**, а не там, где «скорее всего»: тест разбирает синтаксическое
  дерево каждого модуля проекта.
- **Поля ответа проверяются на любой глубине**, а для учётной записи набор полей зафиксирован
  целиком. Новое поле в ответе придётся осознанно добавить в тест.
- **Пройден весь OWASP API Top 10**, а не только четыре пункта из задания; для каждого
  неприменимого пункта указано, почему.
- **Проверки повторяемы**: автотесты идут в общем прогоне, живая проверка запускается одной
  командой и сохраняет протокол.

python manage.py test tests.security        # 45 автотестов безопасности
